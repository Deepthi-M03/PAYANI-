# Deployment

Target: **Netlify** for the frontend, **Render** for the API, **Neon** for PostgreSQL. All on free plans.

| Environment | Plans | Suitable for |
| --- | --- | --- |
| **Staging** | Netlify free + Render free web service + Neon free Postgres | Checking the deployed site. Not for real users: the API sleeps when idle, and reminders only fire while it is awake. |
| **Production** | Netlify free + Render Starter web service (always on) + Render Basic Postgres, optionally a Starter background worker | Real users and reliable reminders. Costs money (about USD 13–20 a month, see ADR 0002). **Not set up until the owner approves the budget.** |

The steps below create **staging** with free plans only. Nothing here creates a paid resource; if any dashboard asks for payment details, stop.

## What gets created

| Platform | Resource | Plan | Defined in |
| --- | --- | --- | --- |
| Neon | One Postgres project (created by hand, free plan, no card) | Free | You create it; paste its connection string into Render |
| Render | `payani-api` web service (API + embedded worker) | Free | `render.yaml` |
| Netlify | Site built from `frontend/`, proxying `/api` to Render | Free | `netlify.toml` |

Secrets: `JWT_SECRET` and `WORKER_TICK_TOKEN` are generated by Render (`generateValue: true`) and never appear in Git. `DATABASE_URL` is the Neon **direct (non-pooled)** connection string, pasted into Render as a secret; it never appears in Git. Render's own free Postgres is not used because it expires after 30 days.

## Steps

1. Push the repository to GitHub (no `.env` is committed; `.gitignore` excludes it).
2. Render → **New → Blueprint** → choose the repository. Render reads `render.yaml` and shows the free web service. Fill in:
   - `DATABASE_URL` = the Neon direct connection string (ends in `?sslmode=require`),
   - `CORS_ORIGINS` = `["https://<your-site>.netlify.app"]` (or leave until step 4),
   - `BOOTSTRAP_SUPER_ADMIN_EMAIL` = the email you will register with.
3. Wait for `https://payani-api.onrender.com/health/ready` to return `{"status": "ok", ...}`. If Render assigns a different URL, update both URLs in `netlify.toml`.
4. Netlify → **Add new site → Import from Git** → the same repository. `netlify.toml` sets the base folder, build command and the `/api` proxy.
5. Open the Netlify URL, register with the bootstrap email, then trigger one manual redeploy on Render: on start it grants that account Super Administrator (only if no Super Admin exists yet).

## Same-origin cookies

The refresh cookie is `SameSite=Strict` and scoped to `/api/v1/auth`. Netlify's proxy makes the API appear on the site's own origin, so the cookie is first-party. Uvicorn runs with `--proxy-headers` so rate limits see the real client IP; Render only routes traffic through its own proxy, so trusting forwarded headers there is safe.

## Free-tier limits (checked 26 Nov 2026)

| Limit | Effect on PAYANI | Mitigation |
| --- | --- | --- |
| Free web service sleeps after 15 min without traffic; ~1 min to wake ([Render docs](https://docs.render.com/free)) | First request after idle is slow; reminders cannot fire while asleep | The app labels reminders "best effort"; optional free wake-up below |
| Neon free: compute suspends after 5 minutes idle; about 100 compute-hours a month per project; at the limit compute is suspended, not billed ([Neon docs](https://neon.com/docs/introduction/limits)) | A keep-alive that holds the API awake 24/7 would exhaust the compute hours mid-month | Do not run a 24/7 keep-alive. The connection pool uses `pool_pre_ping`, so a suspended database is reconnected transparently |
| Netlify's proxy gives up after about 26 seconds ([Netlify docs](https://docs.netlify.com/routing/redirects/rewrites-proxies)); a cold API takes about a minute | A request sent straight to a sleeping API would fail | Handled in the app: every API call first waits for `/health/live` (probes of at most 25 s), shows a "Starting the server…" banner, never signs the person out because the server is slow, and offers *Try again* if it stays unreachable for two minutes. Writes are never sent into a sleeping server and never retried automatically |
| Render free: 512 MB RAM, 0.1 CPU | The forecast model trains in memory after every wake-up | `WARM_FORECAST_ON_START=true` trains it in the background at start (peak about 310 MB measured locally; training time on 0.1 CPU is not measured) |
| Render blocks outbound SMTP on free web services | Email reminders cannot be sent | Leave `SMTP_HOST` unset; in-app and browser-push reminders still work |

### Optional wake-up for reminders (staging)

`.github/workflows/wake.yml` calls `POST /api/v1/internal/tick` with the `X-Worker-Token` header. It runs **only when started by hand** (Actions → Wake API → Run workflow). Its 10-minute schedule stays off: besides Actions minutes, a 24/7 keep-alive would exhaust Neon's free compute hours. To use it, copy `WORKER_TICK_TOKEN` from Render into a GitHub Actions secret of the same name, and set the `API_BASE_URL` repository variable to your Render URL.

## Production checklist (after budget approval)

1. Change `plan: free` to `starter` for `payani-api` in `render.yaml` (or in the Render dashboard), and move the database to a paid Neon plan.
2. Set `ENVIRONMENT=production`, `COOKIE_SECURE=true` (already in `render.yaml`) and `CORS_ORIGINS` to your exact site origin.
3. Add a custom domain in Netlify (Domain management) and let Netlify issue the HTTPS certificate; update `CORS_ORIGINS`.
4. Turn on Render's daily database backups (paid plans) and test a restore into a scratch database once.
5. Never run `python -m payani.seeds.load --profile dev` in production: demo accounts are for local use only.

## Migrations and rollback

- Migrations run automatically on every API start (`alembic upgrade head`); they are idempotent.
- To roll back code: Render → the service → Deploys → choose the previous deploy → Rollback. Netlify → Deploys → previous deploy → Publish deploy.
- To roll back the database schema one step: open a Render shell and run `alembic downgrade -1`. Take a backup first; downgrades drop the tables that migration added.
